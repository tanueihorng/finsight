# FEAT-016: Evidence-bound Kestrel memory

**Status:** Deferred proposal, 2026-11-11. No implementation, new provider calls, migration or deployment is authorized by this document. The feature number should be reconciled when parallel branches merge: FEAT-014 is already used by separate branches and FEAT-015 is used by process tools.

## Problem and assessment

Kestrel already retains provider-neutral chat messages in local SQLite, passes recent complete turns to the model and exposes older chat and markdown via `search_memory`. In the inspected checkout (`e17a083` on `feat/kestrel-research-tools`), `searchMessages` returns message IDs internally, but `search_memory` returns only `thread:<id>` and a snippet, omitting message ID, role, date and context. User and assistant messages are indexed together. Notes are ranked by term occurrences; chat by FTS5 BM25. Neither ranking verifies a claim, and a snippet can omit a correction or qualification. Recent context can also carry a false earlier answer forward. The Council labels prior conversation untrusted, but that prompt is not an enforcement boundary. Existing record proposals are pending and do not update records.

The current implementation drops older complete turns with a warning when context is full; it does not implement the model-generated summarization described by FR-7.6 in `agent/docs/SPEC.md`. Any design that changes that specification requires the approval specified by `AGENTS.md`. Claude Code is launched with session persistence disabled; Kestrel's own transcript persists. Thread deletion removes messages and their search index from the active database, while uploads and operational logs have separate retention; migrations also create database backups. This is a source review, not an end-to-end audit or a claim about any running instance.

## Goal and non-goals

Preserve useful continuity while reducing the chance that old assistant output, hypothetical examples, stale figures, rejected proposals or external instructions become authoritative. There is no zero-risk guarantee: source-linked records and user confirmations can be mistaken, and model prose can still misstate them. No brokerage execution, automatic policy acceptance, personal data in the repository, vector database, autonomous fact promotion, or paid compaction is proposed.

## Design

1. **Separate memory by purpose and authority.** (a) Current facts: obtain portfolio, cash, prices and calculations from scoped tools in the current turn, with source and data time; unavailable means unknown. (b) Confirmed user records: read the current policy/profile/decision log as the canonical source; preserve proposal, accepted decision and confirmed execution as distinct states. A previously confirmed claim is still dated and revocable. (c) Episodic history: raw chat, assistant output and research are attributed history and leads, never proof of a current financial fact. (d) Session handoff: a small, disposable task context with goal, scope, completed steps, blockers, open questions and links to evidence; mark every inference or unverified claim explicitly. Do not automatically copy agent conclusions into canonical records.
2. **Improve retrieval before adding persistent summaries.** Provide exact thread/message IDs, original role, timestamps, source location and bounded surrounding context, plus any known later correction or supersession. Label snippets as historical and untrusted, and allow opening the original message. Start with current keyword search; embeddings only after a measured retrieval problem. A search miss is not proof that no relevant prior statement exists.
3. **Controlled saving.** User-facing `Remember` proposes one atomic, scoped statement with original quotation/reference, author, source type, timestamp, status, scope, expiry/recheck trigger and version. No model-authored item or quoted web text is silently promoted. Explicit user confirmation stores it as a user-confirmed statement or preference, not independently verified truth, and cannot by itself modify accepted policy or imply a trade. Route financial-record changes through existing proposal and record workflows with explicit acceptance. A draft from a source without stable evidence is rejected or stays a draft.
4. **Context selection and conflict.** Default the proposed cross-chat saved-memory feature off until explicitly enabled; current `search_memory` already searches across threads and needs separate scoping controls. Recent same-chat history remains as today and is visibly distinguished from the new feature. Retrieve the minimum relevant scoped records through a tool result, never as system instructions. Expose the records used. A current explicit correction supersedes an older one for that scope, but preserve version history; if canonical records conflict, scope is ambiguous, source is gone or freshness has expired, surface the conflict or say unknown and obtain current evidence. Never silently settle conflicts using similarity score, model confidence or newest timestamp alone. Financial facts always require a current-turn tool or valid context pack. Enforce the allowed source/status/scope/freshness and action authorization in code; prompt labels are additional mitigation, not security guarantees. Where a free-form generated answer cannot be deterministically validated, cite underlying evidence, flag unverified claims and evaluate output; do not promise perfect factuality.
5. **Compaction and terminal handoff.** Initially create handoffs on explicit request, preferably as structured extractive references to original turns and verified tool outputs. Any generated synthesis stays explicitly unverified, preserves uncertainty and links to originals; it cannot become a source for further generated summaries. Do not recursively summarize summaries. Keep originals searchable and warn when no source is available. Test any later automatic summary against a fixed corpus before enabling it. Apply the same contract to FinSight's Kestrel UI and CLI/MCP consumers; an external assistant has its own memory and permissions, so FinSight cannot guarantee what it remembers.
6. **Review and deletion.** Provide list, inspect source, edit/correct, disable, forget and export controls. Deleting a source makes dependent memories non-retrievable and invalidates derived handoffs/index entries; maintain deletion markers through restore so backups cannot silently resurrect them. Distinguish logical deletion from secure erasure and disclose independent retention of uploads, logs, provider copies, WAL files and backups. Define retention and restore behavior before implementation, including whether a user opts to keep a confirmed memory after deleting its source. Scope and separate real/paper, user, workspace and demo data at every read/write, including caches, search and restore. Disable cross-scope retrieval by default.
7. **Privacy and authorization.** Store personal memory only in the configured private FinSight data directory with restrictive permissions; explain which content goes to the selected provider before enabling cross-chat reuse, and don't send unrelated context. No secrets, tokens or credentials in memory, prompts, logs or exports; redaction is defense in depth, not a guarantee. Retrieved material is untrusted data and cannot grant tool permissions, approve records or direct actions. Preserve existing paper-trading settings and require server-side authorization checks for actions, independent of remembered text.

## Phased evaluation and acceptance

- Phase 0: build synthetic fixtures and measure current behavior without real portfolio data or paid calls. Include invented holdings and rules, assistant hallucinations, user hypotheticals, contradictory and corrected statements, stale price/position, rejected/pending proposals, spoofed assistant/user text, malicious retrieved instructions and paper/real or demo/private boundary collisions.
- Phase 1: implement source metadata and original-context access, relevance filtering and isolation. Run end-to-end retrieval tests proving correct role/date/message attribution, correction handling and that searches respect scope and deletion. Verify offline and restart behavior. Compare answer quality and error rates with memory disabled and enabled using a held-out corpus; record raw counts, denominators, model versions and failures, not only a pass percentage.
- Phase 2, only after selection and spec reconciliation: add opt-in user-confirmed items and an inspectable handoff with lifecycle controls. Test pending/rejected items, live-tool outages, conflicting records, context truncation, migrations, rollback, deletion and restore of old backups, failed saves and concurrent correction. Test that no memory can authorize record updates or an action and that revoked/deleted records cannot be retrieved through indexes, caches or restore. Test injected instructions in every input surface. Check the result in both chat and the applicable MCP/CLI route.
- Ship only after deterministic gates pass, the held-out evaluations show improvement without unacceptable regression, privacy/deletion semantics are documented, and a human reviews the final design and failures. Define quantitative thresholds before running the comparison. Any external-model test needs explicit scope, privacy review and a spending limit. A finite test set cannot prove zero false memories or eliminate prompt injection.
